3GPP RCA v6 · Design Proposal

FTA Phase Evaluation Suite

A shadow eval-skill track that checks each FTA phase's output against expected FTA design intent — right after Top Event confirmation, Phase 3.1, Gate A, Gate B, and Phase 3.4 — without touching pipeline state or blocking the run.

Every phase skill keeps running exactly as today — the eval track only observes and appends. Gate A Eval is focal: pivot-pruning discards evidence permanently, so a false "clean passage" verdict there is the costliest mistake in the whole pipeline.

Architecture

Five new skills, one per evaluated phase, run alongside the five existing FTA phase skills without modifying any of them.

Ownership

Audit-only write target

  • Each eval skill appends exactly one entry to a new array, fta_iterations[N].phase_eval_log[] — same pattern as the existing keyword_provenance_audit[].
  • Never writes hybrid_tree, base_events, status, or any field a phase skill owns.
  • Never touches meta.current_phase — cannot block, gate, or redirect the run.

Trigger

Auto-activates per phase

  • Same Cline description-trigger convention as the pipeline skills — fires right after its paired phase skill's output lands in context.
  • Read-only: state file slice in, verdict out. No spec/code/log tool calls of its own.

Mechanism

Rule + judge hybrid

  • Mechanical — deterministic checks against schema, invariants, table isolation, keyword provenance.
  • Judgment — FTA-expert rubric on methodology calls a rule can't decide (was this prune actually justified?).

Per-phase rubric

Every rubric below is derived directly from that phase's own SKILL.md contract and hard constraints — the eval only flags where the actual output diverges from what that phase's own design promises.

STAGE 01

Top Event Eval

3gpp-fta-eval-top-event

Reads: phase2_ecf.top_event_candidates[], observable_symptoms, user_decisions[] (Checkpoint A), keyword_provenance_audit[] (iteration_id=null) · engineer_inputs[] when seed_and_run

Mechanical
  • Every candidate event traces to a provenance audit entry with iteration_id: null.
  • Confirmed top event is a member of top_event_candidates[], or carries source: ENGINEER_PROVIDED under meta.mode == "seed_and_run".
  • Checkpoint A entry exists in user_decisions[] with a populated decided_at.
  • No UE_Trace_log keyword appears anywhere in Phase 1/2 audit entries (table isolation).
FTA judgment
  • Is the confirmed event a genuine top event (an undesired system-level outcome) — not a symptom description, and not a cause guessed ahead of the tree?
  • Is its abstraction level consistent with phase1_scope_filter.procedure — not a sub-step, not the whole call?
  • Does the rationale actually cite missing_events / observable_symptoms to justify picking THIS candidate over the others?
STAGE 02

Phase 3.1 — Build Tree Eval

3gpp-fta-eval-build-tree

Reads: fta_iterations[N].hybrid_tree, input_top_event · keyword_provenance_audit[] (iteration_id=N, tagged skeleton / generate_hypotheses / bind_module)

Mechanical
  • branches[] non-empty; if empty, fallback_used must be set (Step 3 fallback fired).
  • Every branch starts status: "unevaluated", gate_a_result: null, children: [] — the mandated initial state.
  • On the non-fallback path, every branch carries a non-null spec_ref.
  • Zero UE_3gpp_signaling_log / UE_Trace_log entries tagged to this phase — 3.1 never queries logs.
  • Every modules[].file traces to a bind_module output — no invented paths.
FTA judgment
  • Is the branch set a plausible MECE decomposition of the procedure's standardized phases — or is a phase the spec would mandate conspicuously missing?
  • When fallback_used fired: are the hypothesis branches one causal level below the top event — not restating it, not skipping two levels?
  • For branches with modules: []: defensible (pure protocol-timing, no code module) or a code-search miss worth retrying?
STAGE 03 · FOCAL

Phase 3.2 — Gate A Eval

3gpp-fta-eval-gate-a

Reads: hybrid_tree.branches[*].gate_a_result / status, pruned_branches[], open_items[]

Mechanical
  • Every branch's final status is one of the five valid values — no free-text drift.
  • Every pruned_branches[] entry carries non-null evidence.
  • pruned_normal branches have zero children — Step 3 must have been skipped, not just unfinished.
  • open branches appear in open_items[] and nowhere else — bucket membership is exclusive.
  • All-pruned_normal case: the all_phases_normal_failure_not_in_skeleton signal is recorded.
FTA judgment — highest stakes in the suite
  • For every pruned_normal verdict: does the signaling evidence show a genuinely clean, complete exchange — or is the match thin/ambiguous and being over-confidently called "normal" when it should be open? A false prune destroys evidence permanently.
  • Is failure_here vs absent actually justified by the rows returned (explicit error/reject IE vs. zero matching rows) — not a non-error message variant misread as a failure?
  • Were branches matching observable_symptoms.missing_events evaluated first, per the skill's own priority rule?
STAGE 04

Phase 3.3 — Gate B Eval

3gpp-fta-eval-gate-b

Reads: hybrid_tree.branches[*].children[*], gate_b_result, base_events[], rejected[]

Mechanical
  • Anti-laziness: every child of an expanded branch has a non-null gate_b_result — none silently left unevaluated.
  • Child IDs follow <branch.id>.<n> with no gaps or duplicates.
  • Every Gate B keyword traces to expand_failure_modes output or the documented 3-level fallback chain — never a 4th, invented source.
  • base_events[], rejected[], open_items[] partition the children set exactly.
FTA judgment
  • When expand_sub_causes fallback fired: were the resulting children still evaluable at Gate B, or rubber-stamped rejected with no real trace evidence behind it?
  • For base_event_confirmed verdicts: does the matched trace line correspond causally to the claimed mechanism — not just any log line touching the same function?
  • Given the module's actual log macros, does the failure-mode list look complete, or is an obvious error path missing from the children?
STAGE 05

Phase 3.4 — Cross-Reference Eval

3gpp-fta-eval-cross-reference

Reads: fta_iterations[N].cross_reference_findings[]

Mechanical
  • Every finding has both commanded_value and actual_value populated when marked VALUE_DISCREPANCY, or a documented reason for the null — never a silent gap.
  • VALUE_DISCREPANCY is set only if delta crosses the documented threshold (dBm >3, timer >10%, boolean/enum any) — flag both false positives and unmarked real discrepancies.
  • implementation_location traces to a find_implementation output, never inferred.
  • Exactly one finding per confirmed base event — no missing, no duplicate.
FTA judgment
  • Is the significance threshold applied the right one for this IE's actual data type — not the generic 3dB rule mis-applied to a boolean/enum?
  • Does the commanded→actual direction of the delta make protocol sense given the symptom — or does it look like a units/scale mismatch producing a spurious discrepancy?
  • For empty commanded_value_ies (expected more at iteration ≥2): genuinely no governing commanded value, or was find_commanded_values under-queried?

For contrast — what BLOCKING looks like: had FM2 been left with gate_b_result: null instead of an explicit rejected, 3.3 Eval would fail the anti-laziness mechanical check outright (a child silently skipped after the phase claimed completion) and surface immediately, not as a methodology note.

Verdict entry

One entry appended per invocation to fta_iterations[N].phase_eval_log[]. Never read by pipeline dispatch logic — audit trail only. This is the actual entry Gate A Eval would have written for the VoLTE example above.

{
  "phase": "3.2",
  "iteration_id": 1,
  "evaluated_at": "<ISO>",
  "mechanical_checks": [
    { "id": "status_enum_valid", "result": "pass" },
    { "id": "bucket_exclusivity", "result": "pass" }
  ],
  "judgment_checks": [
    { "id": "prune_evidence_strength", "verdict": "concern",
      "rationale": "branch P2 (RRCConnectionReestablishmentRequest) pruned_normal on a single matched signaling row; no confirmation of the response step — borderline for clean passage" },
    { "id": "branch_level_consistency", "verdict": "concern",
      "rationale": "branch P5 evaluated independently while its precondition branch P3 is also absent — possible mis-leveled sibling" }
  ],
  "severity": "warning",
  "summary": "0 mechanical violations, 2 methodology concerns flagged for review"
}

Severity taxonomy

SeverityTriggerAction
BLOCKING A mechanical check failed — provably wrong against schema or hard invariant, not a matter of interpretation. Surfaced to the engineer immediately, inline in the same conversation turn.
WARNING A judgment check flagged a plausible FTA-methodology concern — not proven wrong, needs a human look. Logged and briefly mentioned; engineer decides whether to dig in.
INFO All checks passed, but something's worth recording — e.g. a fallback path fired. Logged only, silent.

Out of scope for this design

  • Phase 3.5 (root cause synthesis) and Checkpoint B (iteration controller) — no tool calls in either, lower fabrication risk; deferred.
  • Blocking or auto-correcting the pipeline — the eval track is strictly observational.
  • Rolling phase_eval_log[] into the Phase 4 report — a possible future extension, not part of this design.
  • Golden-case regression harness — this design defines the rubric and the write contract; wiring it into a batch regression runner is separate follow-up work.
