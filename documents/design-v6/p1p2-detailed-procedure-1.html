The pre-FTA prologue

Phases 1 and 2 don't analyze causes. They prepare the ground for FTA by answering two prerequisite questions: where in the system did this fail? (Phase 1) and what specifically did the failure look like in signaling? (Phase 2). Both questions must be answered before the agent is allowed to hypothesize causes — and both must be answered without ever touching trace data or source code.

Why this ordering matters

If Phase 1's scope is wrong, FTA wastes effort building trees for procedures that aren't the real failure. If Phase 2's top event is wrong, FTA produces a confident-sounding root cause for the wrong symptom. The cost of getting these phases wrong is far higher than the cost of running them carefully — which is why v6 added Checkpoint A after Phase 2 (the user confirms the top event before FTA even starts).

Three principles that govern both phases

1. Sequential narrowing

Scope → symptom → cause. Phase 1 narrows from "5G HO fails" to a specific procedure on a specific RAT in a specific time window. Phase 2 narrows from "the procedure failed" to "the failure manifested as RRCReconfiguration with no following RAR." Phase 3 then asks "why?" — but only because the first two questions are answered.

2. Table isolation (HARD)

Both phases may ONLY query UE_3gpp_signaling_log. Trace data (UE_Trace_log) is forbidden until FTA Gate B. Code search is forbidden in both phases. The Python tool log_query.py enforces this at script entry with exit code 3 on violations — no skill discipline alone, an actual hard barrier.

3. Spec-anchored, not memory-anchored

Both phases derive "what should have happened" from spec_query.py lightweight_procedure, not from the agent's pre-trained memory. Every keyword used in any DB query traces to a spec query result in the same pipeline run. The expected message flow, the primary layers, the key timers — all come from GraphRAG output, never invention.

4. Honest about uncertainty

If Phase 1 hits ambiguities, it HALTS and asks the engineer rather than guessing. If Phase 2's log coverage is sparse, it still produces candidates but marks confidence LOW and lets Checkpoint A surface the situation to the user. Neither phase fabricates evidence to look more confident.

Phase 1 · Principles

Why IS/IS-NOT and not another scoping technique

The IS/IS-NOT structure comes from the Kepner-Tregoe problem-solving method. It works for two specific reasons that matter to an LLM-driven pipeline:

  1. It forces the agent to articulate negatives. "5G NR Band n78" is informative; "5G NR Band n78 but NOT LTE Band 7 in the same area" is much more informative. The negative half tells downstream phases what they can safely ignore.
  2. It yields a discriminator. The biggest IS-vs-IS-NOT gap is the most likely place the failure lives. For "fails on 5G NR n78, succeeds on LTE B7 in same cell": the discriminator is "the 5G-specific layer or the n78-specific config." That's the place FTA should focus first.

The agent does not literally fill out a 4×2 grid in the output, but the reasoning behind the four dimensions (WHAT, WHERE, WHEN, EXTENT) drives scope_filter.condition, discriminator, time_window, and reproducibility respectively. The final RCA report renders the grid for the engineer.

The 4 IS/IS-NOT dimensions

IS (the failure)
IS NOT (similar contexts that don't fail)
WHAT
The failing procedure — e.g. "5G NR Intra-AMF Handover"
Closely related procedures that succeed — e.g. "5G NR Initial Attach"
WHERE
Layers / bands / cells / PLMN where it happens
Layers / bands / cells where the same UE operates fine
WHEN
Conditions at failure — UE state, sequence position, time of day
Conditions when the procedure works normally
EXTENT
Severity, count, percentage — e.g. "100% of HO attempts, always"
The same failure being absent — e.g. "no failure on other procedures"

What the engineer sees vs what the skill does

The engineer types one prose paragraph. The skill silently builds the 4×2 grid as its internal reasoning, but only writes the structured fields to state. The grid appears in the final RCA report (Section 1 of the report template) so engineers downstream can verify the contrasts.

Tool calls allowed in Phase 1

  • Required: spec_query.py --operation lightweight_procedure --need is_is_not — returns primary_layers, key_timers, initiating_message, spec_refs
  • Optional: log_query.py --phase-tag phase1 --table UE_3gpp_signaling_log — confirms the procedure's initiating message actually appears in the capture (sanity check only)

That's the entire tool surface of Phase 1. Two operations, both extremely lightweight. No code search, no trace queries, no other spec operations.

Step-by-step mechanics

1

Extract raw facts from the engineer's prose

Read meta.engineer_input. Parse for the following — each becomes a candidate field or an ambiguity entry if absent:

  • UE model / chipset / firmware version
  • RAT (LTE / 5G NR / NR-NSA / WCDMA)
  • Band(s), EARFCN/NR-ARFCN
  • Network operator / PLMN
  • Test scenario / procedure being performed
  • Failure symptom as described by the engineer
  • Conditions at failure (state, sequence, timing)
  • Reproducibility (always / intermittent / specific trigger)
  • Environment (lab / field / specific cell)

Items not mentioned in the prose are not invented. They go into ambiguities[] for the engineer to fill in if needed.

Readmeta.engineer_input
No tool callspure parsing
2

Build IS / IS-NOT contrasts across 4 dimensions

For each of WHAT, WHERE, WHEN, EXTENT, articulate both columns. The IS-NOT column is generated by considering closely-related contexts where the same UE should work normally — same RAT but different procedure, same procedure but different band, same band but different cell, etc.

Pick the largest meaningful IS-vs-IS-NOT gap as scope_filter.discriminator. This single field is the most important piece of Phase 1 output — it tells Phase 3 where to focus first.

Writes (intermediate)discriminator, condition, time_window, reproducibility
3

Call spec_query lightweight_procedure (required)

Invoke spec_query.py --operation lightweight_procedure --need is_is_not with the inferred procedure and RAT. The GraphRAG returns:

  • primary_layers — typical protocol layers involved (e.g. ["NAS", "RRC", "MAC", "PHY"])
  • key_timers — relevant procedure timers with default durations
  • initiating_message — the spec-defined message that opens the procedure
  • spec_refs — TS/clause references for the procedure

Copy primary_layers into scope_filter.layers. The full spec_lookup is written to phase1_scope_filter.spec_lookup by the Python tool automatically.

Halt condition: if the spec query returns empty (procedure unrecognized), append to ambiguities and HALT — ask the engineer to confirm the procedure name. This is rare in practice and almost always indicates a typo or non-standard procedure description.

Toolspec_query.py lightweight_procedure
Empty resultHALT with ambiguity note
4

(Optional) Signaling sanity check

Trigger only if at least one of these is true:

  • Engineer description doesn't unambiguously identify the procedure (e.g. "handover failure" with no RAT specified)
  • Time window is unclear and signaling can help bound it
  • Confirming procedure presence in the capture would resolve scope ambiguity

Invoke log_query.py --phase-tag phase1 --table UE_3gpp_signaling_log with the initiating message as the keyword and a generous time window. The skill consults the result only to confirm the procedure appears in the capture — it does NOT analyze the procedure's outcome here (that's Phase 2's job).

Hard limit: Phase 1 must not query UE_Trace_log. The Python script enforces this with exit code 3.

Tool (optional)log_query.py phase1
Table restrictionUE_3gpp_signaling_log ONLY
5

Resolve ambiguities

Review the ambiguities[] list accumulated so far. Each entry is a question the skill couldn't answer from the prose + tool results.

Hard rule: ambiguities MUST be empty before Phase 2 begins. If non-empty, HALT the workflow with a prompt asking the engineer to clarify each item. The state file is preserved so the engineer's clarification can be appended without restarting.

The rationale: ambiguities at Phase 1 compound at Phase 2 (the wrong messages get retrieved) and explode at Phase 3 (the wrong fault tree gets built). Halt-and-clarify is cheaper than running the whole pipeline on bad scope.

6

Atomic write to state file

Compose the complete phase1_scope_filter block including completed_at timestamp. Atomic write (.tmp → mv). Set meta.current_phase = "phase2_running". The workflow's next dispatch will trigger Phase 2.

What "ambiguity resolution" looks like in practice

Common Phase 1 ambiguities:

  • RAT not mentioned ("UE handover fails" — LTE or 5G?)
  • Procedure name vague ("attach fails" — Initial Attach? Combined Attach? Re-attach?)
  • Time window absent ("yesterday at the office" — useless for log queries)
  • Reproducibility unclear ("sometimes" — 10% or 90%?)

Each becomes one item in ambiguities[]. The HALT prompt lists them as a numbered list and asks the engineer to clarify before the pipeline proceeds.

Phase 2 · Principles

What Phase 2 produces (and what it deliberately does not)

Phase 2 produces the phase2_ecf block containing:

  • observable_symptoms — the signaling timeline (classified events, missing events, log coverage assessment)
  • top_event_candidates[] — 1 to 3 ranked candidate Top Events for the user to choose from
  • top_event = null · not set by this skill
  • user_confirmation = null · not set by this skill

The v6 split: Phase 2 produces; Checkpoint A decides

v5 had Phase 2 set top_event directly and proceed. v6 splits this: Phase 2 produces a ranked list of candidates; the user chooses at Checkpoint A. The reason for the split is snowball-error prevention: if the agent silently picks the wrong top event, all of Phase 3 builds the wrong fault tree. The user gate intercepts this single most consequential decision in the pipeline.

The four event classifications

Every signaling row retrieved in Phase 2 is classified into one of four buckets. The bucket determines whether the row becomes evidence, context, or a Top Event candidate.

✓normal

Matches expected_flow ordering and timing. No failure indicators. Becomes timeline context only.

⚠anomaly

First deviation from expected flow — wrong message, wrong timing, unexpected cause code. Marks where the procedure went off-script.

↪consequence

Follows from an earlier anomaly. Real but derivative — recovery attempts, retries, reestablishment.

❌symptom

Observable failure indicator at the application level — REJECT, timer expiry, no-service entry. Symptoms become top_event_candidates.

The anomaly heuristics (signaling only)

Anomalies at the signaling layer come from four families. PHY/MAC/RLC anomalies are NOT visible here — those surface in FTA Gate B, not Phase 2.

FamilyPattern in signalingExamples
RRC Timer expiry messages, unexpected state transitions T304 expiry → RRC connection reestablishment attempt; unexpected RRCRelease mid-procedure
NAS REJECT messages with non-zero cause code; unexpected EMM/5GMM state changes ATTACH REJECT cause #11 (PLMN not allowed); SERVICE REJECT cause #7 (5GS services not allowed)
Message gaps Expected message absent within the procedure's timer window RRCReconfigurationComplete never sent after RRCReconfiguration received; ATTACH ACCEPT never received after ATTACH REQUEST
Out-of-order REJECT before request; duplicate messages; ordering inversions RRCConnectionReject before any RRCConnectionRequest; duplicate ATTACH REQUEST within seconds

The three confidence levels for candidates

Tier 1

HIGH

log_coverage is rich AND the candidate has explicit signaling evidence — REJECT with cause code, T-timer expiry message, or unambiguous symptom row.

Tier 2

MEDIUM

log_coverage is partial OR the candidate is inferred from message absence with strong context (e.g. no RAR within the expected window after a clean RACH preamble).

Tier 3

LOW

log_coverage is sparse OR the candidate is inferred from indirect signals. Still presented at Checkpoint A; the user decides whether to proceed, refine, or abort.

Log coverage assessment

Phase 2 computes coverage as a ratio after retrieval. The ratio drives confidence assignment and the ambiguity handling path:

CoverageRatioInterpretationEffect on confidence
rich≥ 0.8Most expected messages present in signalingHIGH possible
partial0.4 – 0.79Some expected messages missing — may be sampling or genuine gapMEDIUM cap
sparse< 0.4Most expected messages missing — capture issue or wrong scopeLOW cap; suggest more capture in ambiguities

Step-by-step mechanics

1

Read scope_filter (slice) and check for refinement context

Slice-read phase1_scope_filter. Extract procedure, RAT, layers, time_window, condition, discriminator.

If phase1_scope_filter.user_refinements is non-empty (re-run path from Checkpoint A "refine"), apply the refinement to the analysis context — typically narrowing the time window or adjusting the expected layers. This is the only Phase 2 path that uses user-supplied context beyond the initial scope.

Readphase1_scope_filter (slice)
Refine pathuser_refinements[] applied if present
2

Get expected message flow (spec_query)

Invoke spec_query.py --operation lightweight_procedure --need ecf. The GraphRAG returns:

  • expected_flow[] — ordered messages with direction (UL/DL), layer, and sequence index
  • key_timers[] — relevant procedure timers (already in scope_filter.spec_lookup but re-confirmed)
  • spec_refs[] — citations for the expected flow

The expected_flow becomes the keyword list for Step 3 and the comparison baseline for Step 5.

Halt: if expected_flow is empty, the procedure isn't recognized by the GraphRAG — should have been caught in Phase 1, so this is a rare integrity error. Halt and ask engineer.

Toolspec_query.py lightweight_procedure (need=ecf)
Outputexpected_flow_source written to state
3

Retrieve signaling timeline (log_query)

Invoke log_query.py --phase-tag phase2 --table UE_3gpp_signaling_log with:

  • --keywords = all message names from expected_flow[]
  • --time-window-* = from scope_filter.time_window
  • --layers = from scope_filter.layers

Returns up to 50 rows with timestamp, layer, direction, message_name, ie_values, cause_code. Plus a compressed key_events list (≤5) for in-context display.

Table isolation enforced by script. Phase 2 cannot touch UE_Trace_log; the script exits with code 3 if requested.

Toollog_query.py phase2
Returnsrows[] + key_events[≤5]
4

Classify each retrieved event

Walk the retrieved rows in time order and assign one of four labels:

  • normal — matches an entry in expected_flow at expected position with no failure indicators
  • anomaly — first deviation from expected_flow (wrong message, wrong order, unexpected cause code)
  • consequence — appears after an anomaly and is plausibly derivative (reestablishment attempt, retry)
  • symptom — explicit failure indicator at application level: REJECT message, T-timer expiry, NoService entry. These are the candidates for top_event.

Capture earliest_anomaly = timestamp of the first anomaly-classified event, or null if no anomaly observed.

5

Identify missing events

For each entry in expected_flow[] whose message name does not appear in the retrieved rows, build a missing_event record:

{
  "expected_message": "RRCReconfigurationComplete",
  "expected_after": "RRCReconfiguration",
  "spec_ref": "TS 38.331 §5.5.1"
}

The missing_events[] list is consumed by Phase 3.2 to prioritize branch evaluation (branches whose mandatory_messages are in missing_events get evaluated first).

6

Build top_event_candidates[] — the v6 ranking algorithm

See §07 for the full ranking algorithm. In summary:

  • rank 1 (primary): the LAST symptom in chronological order — the deepest unrecovered failure
  • rank 2-3 (alternatives): earlier symptoms that pass the defensibility test

Never pad to 3 with hallucinated alternatives. List can be size 1, 2, or 3.

7

Assess log_coverage

Compute coverage = retrieved_present_count / expected_flow_size and bucket: rich (≥0.8), partial (0.4-0.79), sparse (<0.4).

8

Assign confidence per candidate

For each candidate (see §05 for criteria):

  • HIGH if coverage=rich AND explicit signaling evidence (REJECT/timer-expiry/symptom row exists for this candidate)
  • MEDIUM if coverage=partial OR inferred-from-absence with strong context
  • LOW if coverage=sparse OR indirect signals only
9

Ambiguity handling — DO NOT halt

If log_coverage=sparse AND no HIGH-confidence candidate: append a note to phase1_scope_filter.ambiguities[] ("Capture coverage sparse; consider extending capture window") but do not halt the pipeline.

Rationale: Checkpoint A is right after Phase 2. The user sees the sparse-coverage warning, sees the LOW-confidence candidates, and decides whether to refine (add more context), reject and restart (recapture and re-run from Phase 1), or proceed anyway. Halting Phase 2 would deny the user that choice.

The defensibility test (3 criteria · ALL required)

A symptom can become an alternative candidate (rank 2 or 3) only if it satisfies all three of these criteria. The conjunction is deliberately strict to prevent padding the list with weak alternatives.

CriterionDefinitionWhy it matters
Distinct outcome The symptom represents a distinct procedure outcome, not just a consequence of an earlier event in the same chain Otherwise the alternative is just an upstream view of the same failure — adds noise without giving the user a real choice
Own evidence The symptom has its own signaling evidence row (REJECT, timer-expiry, etc.) — not inferred from absence alone If the alternative is purely inferred, the user can't see what makes it defensible — it looks like guessing
MEDIUM-distinct from primary Differs from the primary on at least one of: protocol layer, cause code family, or procedure phase Two candidates that differ only in timestamp are not really alternatives — they're the same failure twice

The "no padding" rule (D3 = 3 cap, not floor)

D3 sets a ceiling, not a target

The locked decision in v6 says "Top Event alternatives ≤ 3". This is a maximum, not a minimum. The candidates list may have:

  • 1 entry — common for clean captures with one clear symptom. Checkpoint A presents it as "PRIMARY (no alternatives meet the bar). Proceed?"
  • 2 entries — primary plus one defensible alternative
  • 3 entries — primary plus two defensible alternatives

NEVER 3 entries when only 1 or 2 are defensible. Inventing alternatives to fill out the menu defeats the purpose of curating it. A single defensible candidate presented for confirmation is more honest — and more useful to the user — than three with two of them weak.

Rejection reasons for non-primary candidates

Each non-primary entry in the list has a rejection_reason field — a sentence explaining why the agent did not pick this one as the primary. This is the engineer's information for the Checkpoint A decision. Typical rejection reasons:

  • "Consequence of primary; not a distinct top event" — failed the distinct-outcome criterion
  • "Earlier in chain but recovers; primary is the unrecovered failure" — the alternative happened first but the procedure ultimately failed at the primary
  • "Different layer but lower confidence; primary has stronger evidence" — both are real symptoms but primary has more support
  • "Same procedure phase as primary; not meaningfully distinct" — failed the MEDIUM-distinct criterion

The rejection_reason for the primary candidate is always null.

What if no symptom event is found at all?

The "no symptom" edge case

If Phase 2 walks the entire retrieved timeline and finds no symptom-class events — only normal, anomaly, and consequence events — there are no candidates to present. The skill then constructs an inferred candidate from the strongest anomaly evidence (e.g. "Procedure incomplete — RRCReconfigurationComplete absent within expected window") with LOW confidence and adds a note to ambiguities.

This is not the same as padding. The single inferred candidate IS the strongest defensible thing the agent can present, and Checkpoint A's "refine" or "reject and restart" options give the user a clean path forward. The alternative — Phase 2 silently producing nothing — would force a halt with no information for the engineer to act on.

Step 6 — Build top_event_candidates[]

Symptoms in chronological order:

  1. 14:02:12.00 — T304 expiry (anomaly, but in the sequence a T-timer expiry is also a procedure outcome → could be a symptom)
  2. 14:02:12.50 — RRC Connection Reestablishment Reject (definitive symptom)

The agent reconsiders: T304 expiry IS the moment the procedure formally failed. The reestablishment reject is the consequence of the HO failure. Both are symptom-class but they describe different things:

  • The first describes the original handover's outcome: 5G_HO_Execution_Failure (no target cell sync after RRCReconfiguration)
  • The second describes the recovery attempt's outcome: RRC reestablishment reject

By the methodology heuristic "primary = last unrecovered symptom", the reestablishment reject is later in time but is a consequence; the HO failure is the unrecovered original event. Primary = HO execution failure.

Now apply the defensibility test to the reestablishment reject as a potential alternative:

  • Distinct outcome? Yes — it's a different procedure (reestablishment, not handover)
  • Own evidence? Yes — REJECT message with cause_code
  • MEDIUM-distinct from primary? Marginal — same RRC layer, different procedure phase. Pass.

The reestablishment reject passes the defensibility test → goes in as rank 2 with rejection_reason "Consequence of primary; reestablishment after HO failure".

Expected_flow had 5 entries; 4 distinct expected messages were retrieved (Measurement Report, RRCReconfiguration, RA Preamble, plus the T304 expiry which is procedure-related though not in expected_flow). Missing: RAR, RRCReconfigurationComplete.

coverage = 3/5 = 0.6 → partial

Step 8 — Confidence assignment

  • Rank 1 (HO execution failure): coverage=partial caps at MEDIUM, BUT the symptom has very strong inferred-from-absence evidence (RRCReconfiguration with sync received, no RAR within T304 window — exactly the textbook signature).   • Rank 2 (Reestab reject): coverage=partial, evidence is direct REJECT row → LOW (because it's a consequence, the strength of evidence doesn't elevate it past the primary)

coverage=partial AND rank 1 is HIGH confidence → no ambiguity note needed. Proceed.

The user's options at Checkpoint A (what Phase 2 enables)

Phase 2's output determines what the user can do at Checkpoint A:

Phase 2 output stateCheckpoint A behavior
single HIGH candidate Confidence is high enough that "confirm" is the obvious choice. The user can still refine or reject, but the path of least resistance is acceptance.
primary + 1-2 defensible alternatives The user sees the full menu with evidence and rejection_reasons. "use alternative 2" or "use alternative 3" are first-class options.
candidate(s) with LOW confidence The agent's recommendation is still "confirm rank 1" but with a confidence note. The user is more likely to choose "refine" to add context, or "reject and restart" to recapture.
no symptom found · inferred candidate Coverage is so poor that the candidate is essentially a placeholder. User should typically choose "refine" or "reject and restart". Checkpoint A's "abort" option is available if the engineer wants to escalate.

The refine path (re-entry into Phase 2)

If the user types /rca refine: <text> at Checkpoint A, the Checkpoint A skill:

  1. Appends the refinement text to phase1_scope_filter.user_refinements[] (an array — multiple refinements accumulate)
  2. Clears phase2_ecf entirely
  3. Sets meta.current_phase = "phase2_running"
  4. HALTs — user types /rca again to trigger the next dispatch

The next dispatch re-runs Phase 2 (this skill) with the refined context picked up in Step 1. Phase 1's scope_filter is otherwise unchanged — only the refinement context shifts what Phase 2 retrieves and how it ranks candidates.

Why refine doesn't restart Phase 1

A refine typically narrows or adds context within the same scope — "look only at 14:02:11-14:02:12 not the whole window" or "include the MAC layer in the timeline". The original scope_filter is still valid. If the scope itself is wrong, the user picks "reject and restart" which DOES restart Phase 1.
