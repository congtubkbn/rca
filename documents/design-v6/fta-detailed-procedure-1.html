FTA philosophy & invariants

Before walking through mechanics, three principles that drive every design decision in the FTA phase. Each constrains what the agent is allowed to do at every step.

1. Hybrid (spec + code), not pure either

A pure-spec fault tree generates plausible-sounding branches that have no anchor in the actual UE codebase — the agent invents file names, function names, and log strings. A pure-code fault tree has the opposite problem: it finds real code paths but can't relate them to 3GPP-defined procedures, so the resulting "root cause" can't cite a spec violation.

v6's hybrid approach binds them: each top-level branch is a 3GPP-defined phase (from spec_query skeleton) with a UE source module assigned to it (from code_search bind_module). Both anchors are required. If a branch has a spec phase but no module, it's marked unbindable; if a phase has no spec basis, it doesn't exist as a branch at all.

2. Evidence gates, not reasoning chains

Every claim the FTA pipeline makes is backed by at least one log row or code snippet retrieved during this same pipeline run. No claim is supported by "the agent thinks this is likely." This is enforced through two gates:

  • Gate A (signaling, Phase 3.2) — every top-level branch must either show clean signaling traffic (PRUNE) or signaling failure indicators (CONFIRM) before progressing
  • Gate B (trace, Phase 3.3) — every failure mode (child branch) must show literal log strings in trace data before becoming a base event

If both gates are silent, the hypothesis is rejected — not "the agent isn't sure." Rejection is the default outcome.

3. Mechanical synthesis, not creative interpretation

The final root cause class (Phase 3.5) is determined by a small decision tree over already-populated state file fields. The agent does not "interpret" the evidence to decide what kind of failure it is — the class falls out mechanically from whether cross-reference detected a value discrepancy, whether multiple base events are linked, whether implementation location was identified, and so on.

Anti-hallucination is enforced by the Python tools, not by skill discipline

The wrapper-skill indirection (the recently-discovered weakness) is documentation only. Real enforcement lives in the Python scripts: log_query.py refuses table-isolation violations; code_search.py extracts log strings only from a fixed set of macros; spec_query.py preserves verbatim spec notation. Every keyword used in any FTA query traces to a prior tool invocation in the same pipeline run — and the scripts auto-append the audit trail so this is verifiable post-hoc.

Phase 3.1 — Build hybrid tree

Goal: produce the top-level shape of the fault tree. Children (failure modes) are NOT added here — that happens in 3.3 only on branches that survive Gate A. This phased construction matters: building children for branches that turn out to be normal-passage wastes tool calls and produces noise in the final report.

Mechanics — step by step

1

Read the iteration's input top event

Slice-read fta_iterations[iter-1].input_top_event. For iteration 1, this came from Checkpoint A; for iter ≥2, it was set by the iteration controller when the user chose "dig deeper" at the prior Checkpoint B.

Readfta_iterations[iter-1].input_top_event
Spec-anchored?iter 1: usually true · iter ≥2: usually false
2

Call spec_query.py --operation skeleton with the procedure name, RAT, and the iteration's top event. The GraphRAG returns a list of standardized procedure phases — each with a unique ID, name, spec reference, expected mandatory messages, and protocol layer.

For a 5G handover failure: typical skeleton returns ~3 phases (RRC Reconfiguration → Target Cell Sync → Reconfiguration Complete). For a deeper iteration drilling into "Preamble_Power_Error", the skeleton likely returns nothing — that triggers the fallback.

Returnsphases[] with mandatory_messages + spec_ref

Detect empty skeleton → fallback path

Why no children yet?

If we expanded P1's failure modes now and P1 turned out to be a normal_passage in Gate A, those failure modes were generated for nothing — wasted tool calls and noise in the report. Phase 3.3 expands only the branches that survive Gate A. This is the central efficiency tradeoff of pivot-pruning: do the cheap discrimination first, then drill.

Phase 3.2 — Gate A pivot-pruning

Goal: classify each top-level branch as normal-passage, failure-here, absent, unclear, or N/A using signaling data only. This is "pivot-pruning" because the result is one-way: branches confirmed normal are removed from further analysis, never re-evaluated. Wrong prune = wrong root cause, so the bar for normal_passage requires positive evidence, not just absence of red flags.

normal_passage

All mandatory messages received cleanly, no failure indicators, expected ordering.

Case B

failure_here

Messages present but with failure indicators: REJECT, timer expiry, retransmission limit reached, missing follow-up.

PROCEED to 3.3
Case C

PROCEED to 3.3
Case D

code-only branch

Mechanics — step by step

1

Prioritize branches with absent-signaling hints

If iteration 1: sort branches so the ones whose mandatory_messages appear in phase2_ecf.observable_symptoms.missing_events come first. Phase 2 already noticed which expected messages didn't appear — those branches are the most likely failure points and worth evaluating first. (Iteration ≥2: just follow tree order.)

2

Optional IE refinement

If mandatory_messages is generic (e.g. "RRCReconfiguration" matches many messages), call spec_query.py --operation extract_ies to get the specific IE names that distinguish this branch's instance. Pass these as --ie-names to the Gate A log query.

Tool (optional)spec_query.py extract_ies
3

Query signaling log for this branch

Call log_query.py --phase-tag phase3_gate_a --table UE_3gpp_signaling_log with the branch's mandatory_messages as keywords, the iteration's time window, and the branch ID as --hypothesis-id. Table isolation enforced at script entry — Gate A cannot touch UE_Trace_log.

Returns up to 5 key events: timestamp, layer, direction, message name, key IE values (KPIs), cause codes if present.

Toollog_query.py phase3_gate_a
TableUE_3gpp_signaling_log ONLY
4

Classify into one of five cases

The skill maps the key_events shape onto the five cases above. Heuristics:

  • Case A normal_passage — all mandatory messages present, no cause codes, expected sequence intact, no timer-expiry markers
  • Case B failure_here — any of: REJECT message, non-zero cause code, timer expiry indicator, max-retx message present
  • Case C absent — keywords_with_hits empty for this branch's mandatory messages
  • Case D unclear — partial hits, ambiguous ordering, or count below expected threshold

Write the result to branch.gate_a_result with the verdict and the supporting evidence snippet.

5

Update branch status and lists

Set branch.status accordingly. Case A → append to pruned_branches[] and skip Phase 3.3. Cases B & C → proceed to Phase 3.3. Case D → append to open_items[] with a note about what's missing, and skip Phase 3.3.

The "all branches normal" halt

Failure not in skeleton

If after Gate A every top-level branch is Case A normal_passage, the skill halts with all_phases_normal_failure_not_in_skeleton. This means: signaling shows the entire procedure completed without obvious failure, yet the engineer reported a failure. Three explanations are possible:

  1. The failure is at a layer below signaling (PHY/MAC/DSP) — needs trace data the FTA pipeline cannot reach because all branches got pruned at signaling
  2. The top event was misclassified at Phase 2 — engineer should refine and re-run
  3. The signaling capture is incomplete (sparse log coverage)

The iteration controller surfaces this at Checkpoint B with a recommendation depending on which signals fire (typically abort with a request for more trace data).

Phase 3.3 — Dynamic expansion + Gate B

Goal: for each branch that survived Gate A (Cases B, C, or N/A), discover its specific failure modes from UE source code and validate each against trace logs. This is where the fault tree gains its sub-branches and where individual base events are confirmed.

The two-step pattern per surviving branch

Step A — Expand failure modes (CODE)

Call code_search.py expand_failure_modes on the branch's bound module. The script searches for error-handling blocks: timeout/retry counters, validation failures, clamp/saturate logic, exception throws. For each block it extracts:

  • A name (e.g. RACH_Timeout, Preamble_Power_Error)
  • Detection code summary (≤80 chars)
  • Log keywords — literal strings from MSG_HIGH/SYS_ERR/etc. macros only
  • Log tags (thread/component identifiers)
  • Function signature

Fallback: if empty, call spec_query expand_sub_causes to get spec-derived sub-causes instead.

Step B — Gate B trace verification

For each failure mode just added, call log_query.py phase3_gate_b against UE_Trace_log with the failure mode's literal log_keywords and log_tags. Three outcomes:

  • CONFIRMED — matched events found → append to base_events[]
  • REJECTED — zero matches → append to rejected[]
  • UNCLEAR — partial/ambiguous → append to open_items[]

Anti-laziness rule: ALL failure modes of a branch are evaluated even if one is already confirmed. Other base events may exist in parallel.

Mechanics — step by step

1

Loop over surviving branches

Process each branch with status failure_here, absent, or not_applicable. Pruned branches and open-items are not expanded.

2

Call code_search.py expand_failure_modes

Per branch, pass the bound module name and the branch's phase context. The script runs three search queries:

  1. "<module> error handling failure paths"
  2. "<module> timeout retry max limit reached"
  3. "<module> validation reject invalid"

From the returned snippets, the script extracts log strings only from this fixed set of macros: MSG_HIGH, NAS_MSG_HIGH, LOG_MSG, QCRIL_LOG_DEBUG, RRC_LOG_MSG, SYS_ERR, DS_MSG_HIGH_1, printf("[TAG]…"), fprintf(stderr, …), syslog. No inference — if the macro literal isn't there, the log_keyword isn't there.

Toolcode_search.py expand_failure_modes
Fallback if emptyspec_query.py expand_sub_causes
3

Append failure modes as branch children

For each failure mode returned, assign an ID <branch_id>.<n> (e.g. P2.1, P2.2), add to branch.children[] with status: "unevaluated", gate_b_result: null.

4

For each child: call log_query phase3_gate_b

Query UE_Trace_log with the failure mode's literal log_keywords and log_tags as filters. Time window from scope_filter. Pass child id as --hypothesis-id.

Keyword fallback chain (stop at first hit, never invent):

  1. failure_mode.log_keywords from code_search
  2. failure_mode.function_signature as message LIKE pattern
  3. extract_ies IE names if available
  4. STOP — mark Gate B unclear

  • partial/ambiguous → status: "open", append to open_items[]

Why both P2.1 and P2.2 are confirmed even though P2.1 looks like a consequence

Phase 3.3 confirms presence in trace data, not causality. P2.1 (RACH timeout) and P2.2 (Preamble power error) both have observable trace evidence — both are base events. Whether one caused the other is a Phase 3.4 question, answered by cross-reference. Confirming both keeps the option of MULTI_CAUSE if cross-ref can't disambiguate.

Phase 3.4 — Cross-reference

Goal: for each confirmed base event, determine whether the UE applied the value the network commanded. A discrepancy between commanded value (in signaling) and actual value (in trace) is the strongest possible root cause signal — it identifies exactly which IE the UE failed to honor, and (via implementation location) which code function was responsible.

This is the critical v4-introduced mechanism, preserved verbatim in v6. It's what makes the difference between "RACH failure" (symptom) and "DSP clamps Tx power at -10 dBm despite -110 dBm commanded" (actionable root cause).

Step-by-step mechanics

1

Identify commanded-value IEs

For the base event, collect the upstream signaling messages — typically the mandatory_messages of the base event's parent branch (the messages that set up the failing operation). Call spec_query.py find_commanded_values with the base event name, layer, and upstream messages.

The GraphRAG returns IEs that the network commanded the UE to apply at this layer. Each entry has IE name, source message, semantic meaning, spec_ref, expected UE action, and range/unit.

Empty result is valid. Many base events have no commanded-value IE — typical of timer-expiry failures or code-internal logic errors. In that case write the finding with commanded_value_ies: [] and a note; Phase 3.5 will classify as ABSENCE or TIMER_EXPIRY.

Toolspec_query.py find_commanded_values
Empty resultvalid → ABSENCE candidate
2

Extract commanded value from signaling

For each commanded IE returned above, query the signaling table with --return-ie-values true to extract the actual value the network sent. The script parses the ie_values JSON column for the specific IE name and returns ie_value_extractions[] with value + units + source message + timestamp.

If extraction returns nothing — the IE was in the spec but absent from this run's signaling — append to open_items[] with note. DO NOT fabricate the value.

Toollog_query.py phase3_cross_ref (signaling)
--return-ie-valuestrue (always for cross-ref)
3

Find actual-value log macros in code

Call code_search.py find_implementation with a description of what the UE was expected to do with the commanded IE (e.g. "DSP calculates and applies transmit power"), the spec IE name as a hint, scope procedure, and scope layer. The script finds code paths where the UE applies this IE and identifies log macros that report the applied value at runtime.

Returns: found (bool), confidence, literal log_keywords/log_tags from the macros that print the applied value, function names, implementation file paths, evidence summary.

If found: false — no code path that logs this IE's application — mark unverifiable, append to open items.

Returnslog_keywords + implementation_files

Extract actual value from trace

Call log_query.py phase3_cross_ref against UE_Trace_log with the literal log_keywords and log_tags from Step 3, plus --return-ie-values true. The script parses numeric values from matched messages using patterns appropriate to the IE type — -?\d+(\.\d+)? dBm, -?\d+ ms, etc. — with the expected unit from Step 1.

5

Compare and classify

Compute delta between commanded and actual. Apply significance thresholds per IE type:

  • Power (dBm): |Δ| > 3 dB → significant
  • Timer (ms): |Δ| > 10% of commanded → significant
  • Boolean / enum: any mismatch → significant
  • Frequency / numeric ranges: any mismatch outside spec tolerance → significant

If significant: root_cause_class = "VALUE_DISCREPANCY" in this finding. Document the threshold used. Otherwise leave class null — Phase 3.5 will assign ABSENCE or another class.

6

Record implementation location and write finding

Set implementation_location from Step 3's implementation_files[0]. Compose interpretation as 1–2 sentences using only populated values (no creative narrative). Append the full finding to fta_iterations[iter-1].cross_reference_findings[].

Repeat all six steps for every confirmed base event. One finding per base event, even when commanded_value_ies was empty.

The six root cause classes

Class Meaning Typical evidence pattern Controller's next-iteration action
VALUE_DISCREPANCY Network commanded a specific value via an IE; UE actually applied a different value. The strongest, most actionable class. Cross-ref finding has commanded_value, actual_value, and significant delta. Implementation location identified. Recommend dig_deeper into the cause-side base event (the one carrying the discrepancy)
ABSENCE Confirmed base event exists in trace but no commanded-value IE applies. Typically a code-internal logic error or missing handling. ≥1 base_event confirmed; cross-ref returned empty commanded_value_ies. Iter 1: dig_deeper; iter ≥2: accept_terminal
TIMER_EXPIRY Single base event is a timer firing. UE waited for something that didn't arrive. One base_event matches timer naming pattern (T3*, T3xx, timeout, wait_for_*). With implementation_location: accept_terminal; without: dig_deeper
MULTI_CAUSE Several base events are confirmed; cross-ref links them but doesn't isolate one as the primary cause. ≥2 base_events; cross-ref findings show interaction but no clear dominant discrepancy. Recommend dig_deeper into the highest-confidence base event
ALL_REJECTED All proposed failure modes failed Gate B — no trace evidence supports any of them. base_events empty; rejected[] non-empty. Recommend abort; Phase 2 may have misidentified the top event
OPEN Insufficient evidence to confirm or reject — typically sparse log coverage. base_events empty; open_items[] non-empty. Recommend abort; need more trace capture and re-run

Synthesis steps

1

Determine root_cause_class via decision tree

Apply the decision tree in Fig. 3 strictly in order — first match wins. Pure boolean logic over already-populated state slice; no fuzzy interpretation.

2

Identify failing_phase

From hybrid_tree.branches[], the branch with status == "failure_here" (or deepest "absent" branch if no failure_here exists). Record its name in failing_phase; record names of all pruned branches in pruned_phases[].

3

Build base_event_chain with cause/symptom relationships

Iterate base_events[]. For each, check cross_reference_findings: if this base event has a VALUE_DISCREPANCY finding, label its relationship as cause_of_<other_id> where the other is also a base event without its own discrepancy. The non-discrepancy base events are labeled symptom.

This is how the chain "P2.2 caused P2.1" emerges — P2.2 has the discrepancy, P2.1 has trace evidence but no commanded value, so P2.1 is labeled symptom and P2.2 is labeled cause_of_P2.1.

4

Compose description from class-specific template

One template per class. For VALUE_DISCREPANCY:

"Network commanded {commanded_ie} = {commanded_value} via {source_msg} at
{source_ts}, but UE applied {actual_value} (observed in trace at {trace_ts}
via {implementation_function}). Delta of {delta} exceeds {threshold}. This
caused {symptom_base_event_name}, which propagated to top event
{input_top_event}."

All placeholders fill from already-populated state fields. No invented prose. 2-4 sentences.

5

Pick implementation_location and spec_violation

Both come from the cross-reference finding if VALUE_DISCREPANCY. For other classes: implementation_location from the deepest base event's function_signature; spec_violation from the base event's spec_ref. Either field may be null if not derivable — never invented.

6

Assemble evidence_chain

Up to 15 entries, in order: iteration context → pruning evidence per pruned branch → Gate A evidence for failing branch → Gate B evidence per confirmed base event → cross-reference values per finding → implementation location reference. Each entry is one line citing the source (signaling row, trace row, code snippet, or spec_ref).

7

Atomic write

Write the complete iteration_root_cause block to fta_iterations[iter-1]. Do NOT modify meta.current_phase — the iteration controller will pick up next.
